## 2. 目录与模块落实规则

跨模块/HTTP/工具的规范DTO统一在core/contracts.py定义并对照本轮JSON Schema回归；模块schemas.py只组合、重导出这些DTO或定义未共享的内部小类型，禁止复制同名异义模型。Router据唯一DTO生成OpenAPI，前端contracts.ts从实际OpenAPI生成并验证；不另写另一份含义不同的amount/current_company字段。04里的Ledger、Knowledge、Memory分别对应modules/ledger、knowledge、memory，Evidence对应evidence；Identity放core/identity，ModelGateway放infrastructure/model。

ORM表集中models.py适合当前十余张小表，避免Alembic漏加载；具体SQL仅在各模块repository。跨表事务由Application service/unit_of_work显式组织，API不得直接拿Session改票。通用类型不导入业务service，仓储不回调Harness。ConversationStatePort按接口注入，不能从Harness import Conversation.service形成循环。

配置集中core/config.py，业务代码不散读环境变量；敏感配置字段repr隐藏、日志禁止dump。prompt模板入版本管理但不能包含密钥和初始金额/演示固定答复。tools.py是工具schema和handler唯一注册位置，新工具必须增加需求映射、权限说明与必要测试。

## 3. 开发创建顺序与可运行边界

先建backend最小项目、迁移与seed、核心policy/仓储/API，再建ModelGateway与真实工具调用纵向切片；同时只建支撑该切片的Web页面。随后补任务/偏好管理、规则CLI、引用和范围交互，再完善证据与故障验证。源码目录随实际模块创建，不一次填满占位文件。

“可启动”至少要求锁依赖安装、PostgreSQL连接与应用角色权限正常、schema/seed已准备、可信演示凭证可用；“核心闭环可验收”再要求真实模型探针、查询/保存/回读、规则/记忆/证据实际工作。完整MVP还必须完成已确认网页交互和全部Must，不能以目录或空API证明实现。

## 4. 配置、数据与交付边界

开发时`.env`在仓库根由工具显式读取，不靠工作目录隐式查找；Compose只向各服务注入所需变量。DATABASE_URL含敏感凭证，应用与维护角色分开；业务API不能覆盖连接目标。运行数据不打进镜像；DEL-006提供清理后的模拟数据库逻辑备份、恢复/重建方式及与初始seed的差异，不打包命名卷或PGDATA。实际凭证、.venv和node_modules排除。

CI不默认使用真实模型密钥；PostgreSQL测试数据库与演示数据库必须独立，备份文件路径也分别管理。详细环境变量和启动步骤见[10](10_部署与运行架构设计.md)，交付验收顺序见[开发计划](../development/02_开发实施总计划.md)。
